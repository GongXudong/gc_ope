## 早期大 KL 的诊断

**连续分布加 MC 不保证 KL 自动变小。** GMM 在 10000 checkpoint 的历史成功记录
只有 2～8 条，参考侧有 16 条。seed 4 的两个历史成功坐标为
`(0.01,-0.03)` 与 `(0.01,-0.01)`；拟合出的两个分量在原坐标中的协方差特征值
均为约 `[1e-10, 1e-6]`，非常集中。

参考分布采出的许多位置，在历史 GMM 下的对数密度极低，因此出现百万级 KL。
额外独立 10000 点检查得到约 2448591，与正式五次均值 2476935 为同一量级。
诊断文件：`logs/refactor_validation/early_gmm_diagnostic.json`。
本次保留原正则化与分量规则，没有顺手更改算法来压低曲线。

FM 还对两个实数案例检查了 RK4 步数从 32 增至 64 的影响；模型拟合不变，
每次 10000 点，1 次 MC，仅用于数值诊断：

- seed 1 / 300000：KL 0.094130151 → 0.094130166，差约 `1.5e-8`。
- seed 4 / 10000：KL 232.914761 → 232.914963，差约 `2.0e-4`。

结果不支持“这两个案例的大 KL 主要由 32 步 ODE 误差造成”的解释；不外推到
所有 checkpoint。正式默认仍为 32 步。诊断保存于 `fm_ode_diagnostic.json`。

## 训练接入

课程测试中四方法都在真实 Push 环境运行短 SAC 学习并产生优化器更新。
这些测试注入了小批成功/失败统计来触发估计器，只验证接入，不是学习效果实验。
另外通过原 Hydra 训练入口完成 **64 步**端到端检查：

```bash
conda run --no-capture-output -n gc_ope env \
  PYTHONPATH=/home/tacmon/workspace/ex_SSD/gc_ope_refactor/src \
  OPENBLAS_NUM_THREADS=1 OMP_NUM_THREADS=1 MKL_NUM_THREADS=1 \
  python scripts/train_policy/train.py \
  env=my_push_omega_estimator algo=sac_for_my_push callback=sac_omega evaluate=my_push \
  experiment_name=refactor_smoke/gmm_pipeline algo.device=cpu train_steps=64 \
  algo.learning_starts=8 algo.batch_size=8 algo.buffer_size=1000 'algo.net_arch=[16,16]' \
  env.train_env.num_process=1 env.evaluation_env.num_process=1 env.callback_env.num_process=1 \
  callback.0.eval_freq=32 callback.0.evaluate_nums_in_callback=2 \
  callback.1.save_checkpoint_every_n_timesteps=64 callback.1.save_replay_buffer=false \
  evaluate.evaluate_nums_in_evaluation=2
```

评估回调在 32/64 步执行、统计成功同步、末尾评估完成，保存
`checkpoints/my_push/refactor_smoke/gmm_pipeline/rl_model_64_steps.zip`。
本次自然评估无成功样本，因此走正常的随机目标回退，`alpha=0`；该运行不提供
